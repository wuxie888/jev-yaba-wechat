# jev-jarvis（macOS）

微信弹出一条消息 → 悬浮窗立刻告诉你**这句话的真实意图**、**风险几级**、**该怎么回**。

Mac 版 V0：**纯只读、零封号风险**——不注入、不 hook、不解密数据库，只是「看屏幕 + 本地模型判断」。

![演示：微信群消息进来 → 面板给出意图、风险分级与三条候选回复 → 点「填入」直接进微信输入框](docs/demo.gif)

## 现在能做什么

| 能力 | 状态 |
|---|---|
| 抓取微信窗口（**微信不在前台也能抓**） | ✅ 窗口 ID 捕获 |
| OCR 读聊天区文字（中文，含左右分句 + 发送者） | ✅ Vision 框架 + ROI，正文识别率 ~95%+ |
| 判断意图（派活/催进度/问进度/批评/要解释/闲聊/约会议/夸奖） | ✅ 零样本 **86.4%**（22 条实测） |
| 风险分级 0–9 | ✅ 实测有效（批评 3–4 vs 派活 2，8 条实测） |
| 行动建议 | ✅ 意图→建议静态映射 |
| **候选回复生成 + 排序** | ✅ 按选中的「话术」生成（内置 9 种，最多同时 3 种）→ 本地模型排序（能压掉踩雷选项） |
| 防刷屏（消息轰炸时不抢跑） | ✅ 停稳 1.2s + 最小间隔 2.0s |
| 悬浮窗跟随微信窗口 | ✅ 非激活式 NSPanel，不抢焦点；按微信所在的那块屏定位（多显示器安全，不跳屏） |
| 悬浮窗外观 | ✅ 微信浅色配色（#F7F7F7 面板 + 品牌绿），系统深色模式下也保持浅色 |
| 微信关闭自动隐藏 | ✅ |
| 点「复制」把候选写进剪贴板 | ✅ |
| 一键「填入」直接打进微信输入框 | ✅ 走「辅助功能」接口写入（不粘贴、不碰剪贴板，见下） |

## 用法

**只想用、不想自己构建**：[Releases](https://github.com/jev-jarvis/jev-jarvis/releases) 有打好的 `.app`（解压拖进「应用程序」即可；第一次打开要右键 → 打开，原因见「打包成 .app」）。

从源码跑：

```bash
# 前提：微信在运行，且已授予「屏幕录制」权限
#（系统设置 → 隐私与安全性 → 屏幕录制；本机已授予）
./start.command           # 启动悬浮窗，Ctrl+C 退出
```

悬浮窗自动贴在微信窗口右侧（右边没空间则贴左侧），微信关掉后自动隐藏。

**「填入」与辅助功能权限**：点「填入」= 通过 macOS 的**辅助功能接口**把候选文字直接写进微信输入框。
不模拟按键、不经过剪贴板、也不需要微信在前台。输入框里已经有你打的字时会**接在后面**，不会覆盖。
写完会**读回来确认**，没写进去就如实报失败，不会假装成功。第一次点会弹系统授权框（系统设置 →
隐私与安全性 → 辅助功能，给运行 `uv run python` 的那个程序/终端打勾）；没授权时状态行会写
「填入失败：未授予辅助功能权限」。想提前授权、不启动悬浮窗也能测：

```bash
uv run python src/fill.py             # 只报权限 + 微信进程状态，不发按键
uv run python src/fill.py "好的，马上"  # 真正填入（需要上面那个权限）
```

单独跑感知层 / 判断层：

```bash
uv run python src/perception.py          # 只读：打印识别到的消息 + 耗时
uv run python src/judge.py "这个需求你今天跟一下"   # 单条消息出判断
uv run python src/judge_zh_test.py       # 22 条中文意图回归测试
```

## 面板读法

悬浮窗是微信浅色配色（#F7F7F7 面板、近黑正文、品牌绿点缀，系统深色模式下也保持浅色），从上到下依次是：

```
等待微信消息…                                  ← 状态行
这个方案今天能给我吗？                            ← 被判断的消息（面板里字号最大）
来自 王总 · 上文：昨天的评审意见…                   ← 上文行（发送者 + 最近一条上文）
催进度                                        ← 意图（8 类之一，加粗）
意图识别率 92%                                 ← 这次判断的把握
● 留神  4/9                                   ← 风险分级（绿 ≤3 / 橙 4–6 / 红 7–9）
先给当前状态 · 给明确的完成时间                    ← 行动建议
候选回复（按合适度排序）                        ← 候选区标题
[高情商话术                  ▾]                 ← 一个话术一组：下拉框就是分组标题
    #1 · 94%  今天下班前给您初稿   [复制] [填入]    ← 组内按合适度排，编号从 #1 开始
    #2 · 41%  我明早一上班就发您    [复制] [填入]
[贴吧老哥 v1.0               ▾]                 ← 第二种话术
    #1 · 57%  行，今晚给你整完
    #2 · 22%  得，我的锅，这就去改
[不用                        ▾]                 ← 第三种：自己选，选上也出它的 #1 #2
```

- **状态行**：`等待微信消息…` → `有新消息 · 等消息停稳…` → `分析完成`；点按钮后显示「已复制候选 #N」「已填入候选 #N」，失败时显示原因（如未授予辅助功能权限）。
- **意图识别率**：判断模型对这次意图的把握，面板上取整显示（实测准确率见下）。
- **风险分级**：是 10 档概率分布的**加权平均，四舍五入到整数**（所以不会出现 `4.7/9` 这种假精度）。实测这个模型的最高档概率从不超过 0.4，分布是平滑的 —— 拿最高档（argmax）当显示值时，三条意思相近的「批评」消息会跳出 1/3/6 三个不同档位，而平均值稳定（派活 2.0–2.4、批评 3.0–4.0、闲聊 1.7），所以显示平均值。
- **候选行**：`#N · XX%` 是本地排序模型给出的合适度百分比，**每条候选都会显示**；右侧是「复制」「填入」两个按钮。
- **话术选择**：**一个话术一组**，每组由它的下拉框开头（下拉框就是分组标题），组内是它写的候选。**每种话术出 2 条，而且故意一稳一放**：前一条稳妥、能直接发出去；后一条把这个人设做足，更皮更夸张。同一语气两种胆量，所以总能挑到一条敢发的、也总有一条更好玩。两条再按合适度排出 `#1`/`#2`。
  - 默认两种话术（高情商话术 + 贴吧老哥 v1.0）= **4 条**；第三个下拉框选「不用」就只用前两组，选上话术就是 **6 条**。
  - **三个话术是三个并发请求**发出的（一个话术一个请求），所以总耗时约等于最慢那一个，而不是三段相加 —— 实测 2 种 0.78 s / 3 种 0.96 s。分开请求还有个好处：语气之间不会互相串。
  - **面板高度只由内容决定**：2 种话术 686 pt、3 种 798 pt、1 种 574 pt，最后一个下拉框下面只留 18 pt 边距。**不跟微信窗口对齐** —— 试过对齐，但微信窗口一放大（实测 990 pt）面板下面就会拖出近 300 pt 的空白，比长度不齐难看多了。没启用的话术不占位，所以也不会在中间留洞。
  - 改选之后**立刻用当前这条消息重新生成**（判断和风险不变，不重读屏幕）。
  - 内置 9 种：高情商话术 / 贴吧老哥 v1.0 / 拒绝加班 / 卑微乙方 / 稳如老狗 / 已读乱回 / 职场黑话 / 阴阳怪气 / 理科直男。
  - **加自己的话术不用改代码**：在 `~/.config/jev-jarvis/env` 里加一行即可 —— 用 `|` 分隔多条，每条「名字=说明」，**同名的会覆盖内置的**（想改内置话术的措辞也这么干）。重启生效，下拉框、分组标题、标签清洗都会自动带上：

    ```bash
    export JEV_TONES="摸鱼大师=像资深摸鱼选手，把活推得漂亮又不失礼|孙子兵法=用兵法/军事比喻说话，比如「先稳住阵脚」"
    ```

    说明是直接喂给模型的指令，越具体越准 —— 说清「什么语气」加上「别变成什么」，比只写一个形容词管用得多。
  - **面板高度跟着话术数量走**（也能跟微信窗口一样长，见下），选择只保留在本次运行里，重启回默认。
- **先判断、后候选**：意图 / 风险 / 建议（本地判断）先出来，候选（API 生成）后到，具体耗时见下；等待候选时标题写「候选回复 · 生成中…」。

## 实测数字（M1 Pro）

| 指标 | 数值 |
|---|---|
| 捕获耗时 | **~5–25 ms**（进程内抓图）。接口偶尔会拒绝（实测屏幕休眠时返回空图），那时自动回退到 `screencapture` 子进程约 180 ms，日志里会标注「抓屏走了子进程」 |
| OCR 耗时（只扫聊天区 ROI） | **~250 ms**（稳定后，实测 245/249/274/318 ms）；进程启动后**第一次约 540 ms**（Vision 框架首次加载，日志里会标注「首次」） |
| 判断耗时（decider-2b 本地，MPS，float16） | **~0.8 s**（稳态，实测 730–930 ms；带 4 轮上下文约 1.1 s）。**启动后第一次约 9–10 s**（模型加载） |
| 候选生成（API，每话术一次并发调用） | ~0.5–1.1 s（DeepSeek deepseek-chat，2 个话术并发） |
| 意图识别率（零样本，22 条中文职场消息） | **86.4%**（多数类基线 13.6%）※ |
| 端到端：消息 → 出意图 | **~2.5 s**（停稳 1.2 s + 抓屏/OCR ~0.45 s + 判断 ~0.8 s） |
| 端到端：消息 → 出候选 | **~3.2 s**（生成与判断并行，之后串行排序 ~0.7 s） |

※ **这个数字的口径**：`src/judge_zh_test.py` 用的是**不带上下文**的单条消息 prompt（那样才能用 22 条孤立
消息做回归）。实际运行时判断层还会拿到最近 4 轮带昵称的对话，所以线上条件比测量条件信息更多。
改判断层的 prompt 时要记得这一点：改完别直接引用这个数字，要么重跑、要么说明口径变了。

**防刷屏机制**：检测到新消息先标「有新消息 · 等消息停稳…」并保留上一轮结果；消息停稳 1.2 s 后才开始分析，且两次分析最小间隔 2 s。群聊刷屏时不会满屏乱跳。

**两段式排序的价值**：API 生成的候选里经常混着踩雷选项。实测「这做的什么玩意」（批评）生成出「哈哈，老板，我这就改！」，本地模型把它压到第 3（6.6%），把「对不起，我马上改！」排到第 1（57.7%）。

## 打包成 .app

```bash
./packaging/build_app.sh        # 生成 ./jev-jarvis.app（约 400 KB）
open jev-jarvis.app             # 或直接拖进 /Applications 双击
```

**为什么是「启动器包」而不是 py2app/PyInstaller**：把 torch + transformers 冻进包里会做出 2–4 GB 的 App。这个包只带 Python 源码（约 400 KB），首次启动时用 uv 在 `~/Library/Application Support/jev-jarvis/venv` 建虚拟环境（依赖已在 uv 缓存里，实测 3 秒完成），之后秒开。**本机没装 uv 也不用管**：启动器（以及 `./start.command`）会自己用官方脚本装好，装不上才会弹框告诉你手动怎么装。

包带来的实际好处：
- 双击启动，不用终端
- **有独立的 TCC 身份**——屏幕录制 / 辅助功能授权归属「jev-jarvis」自己，而不是启动它的终端
- `LSUIElement`：不占 Dock、不抢焦点，纯悬浮助手

**包内 Python 跟着仓库的 `.python-version` 走**（现在 3.12）。启动器会先比对包内虚拟环境的解释器版本，不一致就删掉重建。这一环以前是漏的：包里没带 `.python-version`，uv 就按自己默认值建了 **3.13**，于是 `./start.command`（3.12）和双击 `.app`（3.13）跑的不是同一个运行时 —— 现在两种启动方式是同一个解释器。重建很快（依赖在 uv 缓存里，实测 0.6 秒）。

### 打成 zip 发给别人（或发 GitHub Release）

```bash
./packaging/release.sh            # -> dist/jev-jarvis-0.1.0-macos.zip + SHA256SUMS
./packaging/release.sh --publish  # 顺手建 GitHub Release 并上传（需要 gh 已登录）
```

脚本干四件事：调 `build_app.sh` 构建、**把 zip 解压回来再验一遍**（解出来必须是带执行权限的 `jev-jarvis.app`，否则直接报错退出 —— 坏包不会悄悄发出去）、算 SHA256、打印发布命令（`--publish` 就直接执行）。**版本号只有一处**：`pyproject.toml` 里的 `version`，包内 `Info.plist` 和 zip 文件名都跟着它走，发新版先改那里。

**发给别人的时候要说清两件事**：

- **第一次打开**：右键（Control+点）→ 打开 → 再点「打开」。没做 Apple 公证（要 99 美元/年的开发者账号），对方 Mac 上直接双击会被 Gatekeeper 拦住 —— 只需这一次。
- **第一次启动**：先联网装依赖，然后按提示授予「屏幕录制」并**退出重开**（见下一段）。

有开发者证书可以顺手签：`./packaging/release.sh --sign "Developer ID Application: 你的名字 (TEAMID)"`（本机没证书，只验到 ad-hoc 那一步）。

**第一次启动必须授权**：系统会弹「需要录制屏幕」——去 系统设置 › 隐私与安全性 › 屏幕录制 打开 jev-jarvis，**然后退出重开**（macOS 要求重启进程才生效）。没授权时面板会红字提示原因，不会静默消失。

**窗口控制**（原生红绿灯）：
- 🔴 关闭 = 退出应用
- 🟡 最小化 = 收起 / 展开面板（滚成一条，仍可看意图）
- 🟢 缩放 = 隐藏（HUD 是固定尺寸）

菜单栏还有 **J 图标**：显示/收起、暂停读屏、立即重新分析、退出。

## 配置

**两层，两个 key，都可以不填**——判断层不填就是本地模型，功能照常。

| 层 | 干什么 | 用什么 | 不填 key 时 |
|---|---|---|---|
| **判断层** | 意图 + 风险 | **TypeSafe Jev**（无嘴模型，只出类型化概率，不写文本） | 本地 decider-2b（首次下载约 7GB） |
| **生成层** | 写回复候选 | 任意 LLM（**Jev 是无嘴模型，写不了文本，这层必须另配**） | 候选区空着 + 启动时弹窗提醒 |

变量名都是**通用约定**，跟你 shell 里其它工具的写法一致：

```bash
mkdir -p ~/.config/jev-jarvis
cat > ~/.config/jev-jarvis/env <<'ENV'
# ① 判断层 —— TypeSafe Jev（不填就用本地 decider-2b，功能照常）
export TYPESAFE_API_KEY=""
export TYPESAFE_BASE_URL="https://api.typesafe.ai"
export TYPESAFE_MODEL="jev-latest"

# ② 生成层 —— 任意 OpenAI 兼容端点
export OPENAI_API_KEY="sk-你的key"
export OPENAI_BASE_URL="https://api.deepseek.com"
export OPENAI_MODEL="deepseek-chat"

# ③ 生成层的另一种写法 —— 任意 Anthropic 兼容端点（和 ② 二选一）
# 两个都填了 key 时 ② 优先；只填一组就够，不用两组都填
# export ANTHROPIC_API_KEY=""
# export ANTHROPIC_BASE_URL="https://open.bigmodel.cn/api/anthropic"
# export ANTHROPIC_MODEL="glm-4-flash"
ENV
chmod 600 ~/.config/jev-jarvis/env
```

②③ 是**二选一**：填任意一组就够（看你的端点是 OpenAI 形状还是 Anthropic 形状）。**两组都没填时**，启动会弹一个对话框提醒你 —— 意图和风险照常工作，只是候选区是空的；填好之后就不再弹。

**只管一个文件**：所有配置都在这一个 `env` 里，`KEY=值` 一行一个（`export` 可写可不写）。**不提供第二种配置文件格式** —— 两个能放同样设置的文件，就是你会去改那个没被读取的那一个。

**配置文件放哪**——两个系统约定都支持，按顺序查找，先命中的生效：

| 顺序 | 位置 | 适合谁 |
|---|---|---|
| 1 | `$XDG_CONFIG_HOME/jev-jarvis/`（设了才查） | 严格 XDG 用户 |
| 2 | `~/.config/jev-jarvis/` | 开发者工具惯例（`gh`/`uv`/`git` 都在这） |
| 3 | `~/Library/Application Support/jev-jarvis/` | **macOS 原生**（GUI 应用惯例，本项目的 venv 也在这） |

每个目录里放一个 `env`（shell 格式，`KEY=value`）。优先级：**真实环境变量 > `env` 文件 > 项目 `.env`**。

> 不想把密钥落在磁盘上？用 macOS 钥匙串，`env` 里改成 `export OPENAI_API_KEY=$(security find-generic-password -s jev-jarvis -w)` 即可。

> `.app` 从访达启动**不继承 shell 环境变量**，所以启动器会自动 source `~/.config/jev-jarvis/env`；Python 也直接读它，三种启动方式一致。

### 用官方 Jev

原生 API 是排队制的。没拿到名额可以用**兼容网关**（key 换成网关的）：

| 网关 | `TYPESAFE_BASE_URL` | `TYPESAFE_MODEL` |
|---|---|---|
| TypeSafe 官方 | `https://api.typesafe.ai` | `jev-latest` |
| OpenRouter | `https://openrouter.ai/api/v1` | `typesafe/jev-1.13` |
| Vercel AI Gateway | `https://ai-gateway.vercel.sh/typesafe` | `typesafe-ai/jev` |
| Opper | `https://api.opper.ai/v3/compat` | `jev` |

Jev 调用失败时（key 过期、网关抖动）会**自动回退到本地模型**并在面板标注，不会让面板失效。

### 生成层可选端点

格式按 URL 自动识别（含 `anthropic` 走 Anthropic 格式，其余走 OpenAI 格式）：

| 服务 | Base | 模型 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat`（实测最快，~0.7 s） |
| 智谱 | `https://open.bigmodel.cn/api/anthropic` | `glm-4-flash` |
| Ollama 本地 | `http://localhost:11434/v1` | `qwen2.5:7b` |

用本地 Ollama 可以做到**完全不出网**。

> **别用带思考（thinking）的推理模型**：DeepSeek 的 `deepseek-flash` / `deepseek-v4-pro` /
> `deepseek-v4-flash` 都属于这一类。它们会先吐一大段思考再给正文，而本应用只给 `max_tokens=300`，
> 于是额度会被思考吃光，**候选区拿不到任何文字（实测 0 条）**——面板会显示「候选生成失败」，但看起来
> 就像「没生成出来」而不是「模型选错了」。要确定可用就用 `deepseek-chat`。

自查（**不打印完整 Key**）：

```bash
uv run python src/generate.py --check     # 生成层凭据
uv run python src/judge_jev.py            # 判断层 TypeSafe 连通性
```

**凭据解析以 Key 为准**：提供 key 的那个来源同时决定端点和模型——否则会拿着 A 家的 key 请求 B 家，然后 401 得莫名其妙。

## 架构

```
微信窗口 ──screencapture -l <wid>──▶ PNG ──Vision OCR──▶ 文本块 (x, y, conf)
                                                            │
                                            过滤 UI 噪声 + 左右分句
                                                            │
                                                      最新一条消息
                                                            │
                                            ┌───────────────┘
                                            ▼
                             decider-2b（本地推理：8 意图 + 风险，一次前向）
                                            │
                                            ▼
                                      悬浮窗 NSPanel

判断层和生成层拿到同一份上下文：最近 4 轮对话，**每轮都带「谁说的」** ——
   王总: 这个方案今天能给我吗
   我: 我下午看一下
   王总: 那数据一起发我
   ← 被判断的是这一条：「今天几点前要？」
```

关键设计：
- **抓窗口而不是抓屏**：`screencapture -l <windowid>` 只取微信自己的内容，所以悬浮窗浮在上面也不会污染 OCR；微信被别的窗口挡住也能抓。
- **不注入、不 hook、不碰数据库**：微信感知不到，没有封号风险（对比 root/Xposed 路线 2025-09、2026-09 两波封号潮）。
- **模型可插拔**：换 `src/judge.py` 里的 `Judge` 实现即可（decider-2b / laya-multilingual / 将来微调的模型）。
- **本地推理用 float16，不要用 bfloat16**：MPS 对 bf16 的算子覆盖不全，会退化到慢路径甚至 CPU。
  同一个 prompt、同一个模型实测：**bf16 1352/1393/1467 ms vs fp16 734/745/827 ms**。判断层是稳态里最大的一块，
  换 dtype 等于把端到端砍掉约 0.6 s，而且 22 条意图回归的准确率**一模一样**（0.864，连错的 3 条都相同）。
- **上下文带昵称**：两层看到的是同一份「最近 4 轮 + 谁说的」。昵称来自群聊里气泡上方的昵称行；
  单聊没有昵称行，用「我 / 对方」代替。实测带上下文后候选会接上话茬（同一句「今天几点前要？」，
  不带上下文只能编一个时间点，带上下文会知道要交的是「数据和方案」）。被判断的那条**不会出现在自己的上下文里**。

## 已知限制（V0 边界）

- **左右分句靠 x 坐标**：聊天区中线右侧判为「自己」，非对称布局可能误判。
- **图片/表情包消息读不出内容**，会跳过。
- **引用回复**目前当普通文本，没区分引用体和正文。
- **微信改版会让布局常量失效**：`src/perception.py` 顶部的 `CHAT_PANE_X_MIN` 等常量需重新校准。
- **「填入」的权限挂在进程上**：现在跑的是 `uv run python`，所以授权对象是终端/Python 而不是一个
  正式的 .app；换终端、换 venv 后可能要重新授权（打包成 .app 就没这问题）。
- 判断模型冷启动加载约 10–20 s。

## 排查（觉得慢 / 不对）

每次分析都会往日志里写**分阶段耗时**，一眼能看出卡在哪一段。觉得慢就把这几行贴到 issue 里：

```bash
tail -40 ~/Library/Logs/jev-jarvis.log   # 两种启动方式都写这里

tail -f ~/Library/Logs/jev-jarvis.log    # 想实时盯就加 -f
```

（`./start.command` 启动时终端里也会同步打印一份，格式相同。）

```
[00:13:22] 读屏 抓取 251ms + OCR 557ms = 808ms · 读到 4 条（对方 4 条）
[00:13:22] 新消息 · 等停稳 1.2s 再分析（两次分析最小间隔 2.0s）
[00:13:24] 开始分析 · 这条消息出现到现在 2.0s
[00:13:36] 判断 12117ms → 闲聊 把握 85% 风险 4.9（首次，含本地模型加载）
[00:13:36] 生成 864ms · 2 个话术并发 → 4 条候选
[00:13:37] 排序 782ms（本地模型，一次前向）
[00:13:37] 端到端 12900ms · 从分析开始到候选上屏
```

**日志里没有消息正文、没有候选文字** —— 只有耗时和数量，所以贴出来是安全的。

**第一次都慢**：进程启动后的第一次 OCR 约 540 ms（Vision 首次加载）、第一次判断约 12 s（本地模型现加载），
日志会在这两行末尾标「首次」。稳定之后是 OCR ~250 ms、判断 ~0.7 s。

**「第一下特别慢」是正常的**：启动后收到的**第一条**消息会慢十几秒，因为本地判断模型要现加载
（上面那行 12117ms 就是它，日志里会标注「首次」）。从第二条起判断约 0.7 s。
嫌慢的话把判断层换成 TypeSafe Jev（`TYPESAFE_API_KEY`，走网络不用加载本地模型），
或者让应用早点启动（模型在第一次分析时才加载）。

## 下一步（按优先级）

1. **攒标注数据**：零样本 86.4% 已能用；把误判的（尤其「催进度 vs 问进度」）记下来，微调能到 95%+。这是目前唯一有明确收益的模型侧改进。
2. **候选生成改流式**：现在是非流式——三条候选全部生成完才一次性返回，实测要等约 1.7 秒；改成流式后**首字约 0.6 秒**就能上屏（同一端点两次独立测量：599ms / 610ms）。改动落在 `src/generate.py`（解析 SSE）与 `src/hud.py`（候选边到边显示，本地排序结果回来后再重排）。
3. **推理模型的失败提示说清楚**：带思考（thinking）的模型会把 `max_tokens` 耗在思考上、返回 0 条候选，而面板只写「候选生成失败: 空结果」，容易被误判成「没生成出来」而不是「模型选错了」。可在检测到「只有思考、没有正文」时直接提示换模型。
4. **补演示素材**：README 缺一张静态的悬浮窗截图（顶部的 GIF 能看懂流程，但截图更适合放进帖子/社交预览）。
5. **区分「聊天消息」和「分享的文章卡片」**（优先级不高）：群里分享的公众号文章，卡片上的作者/日期和文章正文会被 OCR 当成消息，于是面板会去「解读」一篇讲 AI 的文章。感知层目前分不清这两者。可行的过滤特征：`听全文`、`阅读`、链接类卡片；风险是误杀正常消息，所以要做成保守规则。
6. **启动预热（判断模型 + Vision）**：日志显示**启动后第一条消息**的判断要 12 s（本地模型现加载）、第一次 OCR 要 540 ms（Vision 首次加载），端到端 12.9 s；之后每条约 0.7 s + 250 ms。用户反馈的「慢」多半就是这个一次性开销。可以在启动后立刻在后台跑一次空转（加载模型 + 识别一帧），别等第一条消息进来。

已经做完、不用再做的（曾经列在这里）：候选回复生成 + 本地排序、`Judge.judge(context=...)` 的历史上下文（`src/hud.py` 已在传最近 4 条）、打包成 `.app`（用的是启动器包，不是 py2app——原因见「打包成 .app」一节）。
